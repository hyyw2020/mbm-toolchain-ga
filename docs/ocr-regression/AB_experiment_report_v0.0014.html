专项回答：现状 NMS 是否完全不起作用？

是。 现状顺序下 NMS 抑制 0 个框，对「DB 重叠重复框」完全不起作用；且候选顺序 (b) 下 NMS 同样抑制 0 框—— 即这 30 个合成场景里根本没有 DB 重叠重复框可抑制。
推论：v1.0.30 引入 NMS 的立论前提（DB 密集处输出重叠框）未被本 30 场景合成套件复现；NMS 的 IoU 逻辑有单测覆盖、正确，只是未被端到端触发。 真实密集游戏截图是否会触发 = 不确定，需真机验证。

3. 顺手验了什么

  • 红队「score 是 logit」被证伪：真实模型实测输出 shape (1,18,18710)、每时间步各类概率和 = 1.0000、最大 = 1.0 → 图已含 Softmax，score 确为 [0,1] 概率，非 logit；0.4 门槛有效。
  • Fix-B 顺序真相：OcrEngine.kt:206 是 nmsBoxes(mergeSameRowBoxes(detect(src))) = 先合并后 NMS，与文件头旧注释「先 NMS 后合并」相反——本轮已把注释对齐真实代码。
  • 多旋转门控无高置信短路：OcrEngine.kt:752-779 四向 cands.maxByOrNull { it.second }，无阈值早退（用户最担心风险未发生）。
  • NMS 无面积/高度过滤：OcrEngine.kt:546-559 仅 IoU 比较，本轮未加任何过滤（符合硬约束）。
  • Release 构建配置无静默失效：确认 isMinifyEnabled=false、isShrinkResources=false、ABI 仅 arm64-v8a + universal、签名 fromProjectEnv → release 与 debug 行为一致。
  • 全部 Python 改动 py_compile 通过，test_round3.py 全绿（10 条，含 2 条 score<0.4）。

4. 需真机验证什么

  • 真实密集游戏截图是否会触发 DB 重叠框：决定 NMS 是否有意义、以及是否要重排顺序。本合成套件（30 场景）未复现，结论待真机。
  • 镜像 ↔ Kotlin 的 warpCrop 边缘差异：Python 镜像 warp_crop_fixed 与 Kotlin OcrEngine.kt:957-960 在边缘 1px 钳制上口径一致，但落地真机后仍需复验视觉对齐。
  • 拆 APK 确认 assets/ocr/ 仍在：构建配置类（签名/R8/ABI/资源压缩）改动常静默失效，建议每轮 release 人工 diff + 拆包核对。

5. 不确定点

  • NMS 在真实场景的必要性：本轮数据无法证明、也无法否定。若真机复现 DB 重叠框，候选1 重排顺序可能才有意义（届时需重跑 A/B）。
  • Fix-C 行为影响：Python 镜像 clamp 改动被 warp_crop_fixed 遮蔽，对 30 场景零行为影响；其价值仅在「直接调用 ppocr_pipeline.warp_crop 且框越界」时体现，目前无此类入口。
  • 8 个 fail 是模型极限，非回归：属 PP-OCRv6 形近字固有误差，需更强模型或更大词典，本轮不修。

6. Release 口径

  • 本轮 release 包 不含 Fix-A/Fix-C 任何 Kotlin 行为改动（OcrEngine.kt 仅一行注释，零行为影响）。
  • release 与 debug 行为一致，30 场景验收 = 22/8，与 v0.001.3 完全一致。
  • 如需出包，建议仅核对构建配置（无 R8 / 无资源裁剪 / ABI 正确 / 签名到位），并拆 APK 确认 assets/ocr/ 仍在。
