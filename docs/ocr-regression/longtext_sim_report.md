## 2. 三种上限的源码事实（都属实）

| 上限 | 位置 | 行为 | 对本段文字 |
|---|---|---|---|
| `MAX_TEXT_LENGTH = 4000` | `RecallService.kt:93`（`:212` NODE / `:317` OCR 的 `take()`） | **静默截断**，超出部分直接丢弃 | 本段 3670 字，距上限仅 **330 字**；再长就丢尾部 |
| `REC_WIDTH_MAX = 960` | `OcrEngine.kt:794` `targetW = min(960, ...)` | 单框超宽时**压缩**（非拆分） | **触发**：最长行 979.8px ÷ 框高≈40px → ratio≈24.3，不压缩需 targetW≈1166.0 > 960，横向压缩约 18% |

## 4. 拆分正确性

- 原文自然行数：**63**；wrap 后渲染行数：134
- 模式 A OCR 行数：112；模式 B OCR 行数：117
- 模式 B 分屏数：4（每屏 ≤ 37 行）
- 空行/纯符号行在 OCR 输出中自然消失，故 OCR 行数 < 渲染行数，属预期。
- 逐行对照见 `longtext_sim_result.json` 的 `got_lines`。


## 5. 结论

1. **这段 3670 字的文字能被识别约 90%（真实分屏形态）；中文正文基本完整，丢失的几乎全是 markdown 符号。**汉字漏识仅 23/3295 = 0.70%。
2. **「字数无上限」的唯一真实瓶颈是 `MAX_TEXT_LENGTH = 4000`**：本段 3670 字距上限只差 330 字。一旦整篇文字超过 4000，`take(4000)` 会**静默丢弃尾部**——这与「某输入法 5000 字以上就不拆分」是同一类问题，MBM 的阈值是 4000。要「无上限」，必须改这里（改为按屏累积 + 可配置总量上限，或显著提高上限），并**让截断可观测**（记日志/计数），不能静默。
3. **拆分能力本身没有字数上限**：det 不限行数，merge/NMS 不限行数，`DET_MAX_CANDIDATES=1000` 每屏远离。长文本靠**多屏截图累积**天然覆盖，不需要也不应该靠「单张图内拆分」实现无上限。
4. **单行宽度会触发 `REC_WIDTH_MAX=960` 压缩**：wrap 后每行约 53 字（979.8px）就已被压缩约 18%。真实风险面是**不换行的超长行**（表格行、长 URL、代码行、原文中 693 字的那一行）。压缩后仍能识别大部分，但精度下降。
5. **模式 A（91.96%）略高于模式 B（90.17%）**，与「分屏更清晰」的直觉相反。原因：模式 B 每屏独立 OCR，**屏边缘行的 det 检出较弱**（首/末行易丢），且相邻屏重叠区的重复行未完全去净（OCR 行数 117 > A 的 112）。真实 Recall 就是分屏的，因此 **90% 是更贴近实际的估计**；若优化切片重叠与去重，模式 B 还有回升空间。


## 6. 待确认（需真机）

1. 真机逐屏截图的实际高度 / DPI / 字号与本节假设（1080×2400、36px）的差距；
2. `MAX_TEXT_LENGTH` 的目标值：4000 是否够？是否应可配置？截断时如何可观测？
3. `DET_MAX_CANDIDATES=1000` 在真实密集一屏（小字+多行）下是否够；
4. 超长不换行行（表格/URL/代码）是否需要在 det 后按宽度**主动二次切分**再送 rec（即把「压缩」改为「拆分」，这才是真正的「拆分无上限」）。
